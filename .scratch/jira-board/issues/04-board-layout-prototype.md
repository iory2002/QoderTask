# 看板布局原型

Type: prototype
Status: resolved

## Question

泳道 + 列 + 卡片 + 阶段徽章的信息密度到底够不够看？这个尺寸关系没法靠形容词定，得拿一个能看的东西来反应。

做一个静态 HTML（浏览器直接打开，不接触扩展、不接真实数据），必须能表达：

- 600 / 900 / 1400px 三档宽度下，4 列（To Do / In Progress / In Test / Done）× 3 条泳道的挤压情况
- 一张卡在最小状态下能放下什么，在 hover / 展开时多出什么
- 五种阶段徽章 + Build failed 的视觉区分度，用假的 `NEX2-373` 类 key
- 软闸门弹窗（列「未合入」「构建未通过」两条缺失）与必填字段表单弹窗各一屏

## 交付

一个 HTML 文件，路径记在本票的 resolution 里。它只回答「看起来对不对」，不回答「技术上怎么做」——样式直接用内联，避免把 WebView 的缓存问题带进原型判断。

## 原型已交付

**文件：[`prototype/board.html`](../prototype/board.html)**（零依赖，浏览器直接打开）

已实现：

- 5 列（To Do / In Progress / In Code Review / In Test / Done），不分行，每列头部带计数
- 顶栏：项目 chip（MAGR3 / NEX / NEX2 / IB）、「只看我的」（默认勾）、宽度切换 600 / 900 / 1400、同步时间
- 卡片：类型图标 + key + 三行截断标题 + 优先级 + Epic 橙色 chip + 头像 + 评论计数 + 阶段徽章
- 六种阶段徽章：未提交 / MR 待审 / 已 Approve 待合入 / 已合入待构建 / 已构建 / Build failed
- 拖拽真实可拖：跨两列会被拒并提示「只能先推到 X」；往回拖提示「去 Jira 网页」；推进 In Test 且阶段未达标时弹**软闸门**；正常推进弹**transition 表单**

## 待你判断

1. **密度**：1400px 下五列是否卡得太窄（当前卡宽 ~288px，标题截三行）？
2. **阶段徽章与列信息是否重复**：卡已经在 `In Test` 列了，还显示「已构建」徽章有必要吗？
3. **Epic chip**：需要吗？还是省略它、把位置留给标题？
4. **Done 列**：现在全部展示，是否该深色虚化或只显最近 N 张？

反馈后就关闭本票并解锁 05 号票。

## Answer

用户确认以原型为设计基线，四条全部同意：

1. **密度**：卡宽 288px，标题截 3 行；<900px 改为横向滚动，不上下堆叠（看板语义要求列并排）。
2. **列与阶段徽章同时保留**：列 = Jira 状态，徽章 = 交付阶段，两者是不同事实，不去重。
3. **Epic chip**：仅当有 epic 时显示，单行截断。
4. **Done 列**：全部展示但灰化降噪，不折叠。

原型即设计基线：[`prototype/board.html`](../prototype/board.html)。
