# 08 出口与提醒：评审要点单、构建失败、催审文案的模板与边界

Type: grilling
Status: resolved
Blocked by: —

## 由 07 并入（原票已关闭：聚合数字无独立价值）

- MR 卡：`has_conflicts` → 卡面红字（要求立刻动手）；`blocking_discussions_resolved=false` → 只进详情（常是“等作者回复”，上卡面会满屏红点）
- Jira 卡详情：`合入后 N 天未推进`（用 `card.mrs[].mergedAt`，不是 `updated`）
- 两个字段都由 GitLab MR 列表默认返回，不新增请求

## Question

只读工具里，"能动手"的最后一公里全靠复制和深链。要把每种出口的**内容模板**和**触发时机**定死，避免做成十个半成品按钮：

1. **评审要点单**（已在 MR 详情里给"复制评审指令"，现在要更值钱）：模板里放什么——改动文件按模块分组、是否触及配置/迁移/公共接口/构建脚本、关联 Jira 卡的验收点、谁已 approve / 还差谁、以及"重点看哪里"的建议。要不要先调 `/diffs` 统计文件数与增删行（代价：一次额外请求）。
2. **催审文案**：生成一句可直接贴进群里的文本（MR 链接 + 已等时长 + 还差几个 approve + 谁没审）。触发：手动点，还是"超过 N 天"时在卡上出现按钮。
3. **构建失败**：卡上直接显示「构建失败 #245（可点）」+ 一键复制 `卡 key + 构建链接 + 失败阶段 + 失败时间`。不造本地待办（会和 Jira/GitLab 重复）。
4. **本地提醒的边界**：允许哪种——a) 只在板内标红；b) VS Code `window.showWarningMessage` 一次性提示（每天最多一次）；c) 状态栏闪烁。是否要有"别烦我"开关。
5. **失败与降级**：取数失败时这些按钮要不要禁用（避免复制出半截信息）。

## 完成标准

每种出口：一段模板文本样例 + 触发条件 + 数据来源 + 失败时行为，写进 `research/08-copy-exits.md`。模板要能直接拿去实现（含变量命名）。

## 已定（第一轮）

- **Q1 → (a) 只写可证明的事实**：文件数、按目录分组的改动清单、是否触及 `*.vcxproj` / 迁移 / 构建脚本 / 公共头文件、关联的 Jira 卡。不给“建议重点关注”这类主观判断（错的事实比没有事实更糟，且会让人不再看这张单子）。成本为零：`startReview` 已经拉了 diff（`getMrDiffs`，≤3 页 × 100 文件）。
- **Q2 → 冲突上卡面**（红字标签）；未解决讨论只进详情；“合入后未推进”阈值默认 **3 天**、写死不提供配置。
- **Q3 → 不做催审文案**：催审是社交动作，生成一段话不会让人更容易开口；“谁没批”详情里已有。
- **Q4 → (c)**：只在“从未成功取过数”时禁用；`stale` 时照常可用，文案里标注“取自上次成功数据”。
- **Q5 → 不做 toast**：板没开时活动栏角标已在承担提醒；为一个 toast 引入持久化不划算。
- **Q6 → 卡面红字可点，不做复制**（判定口径见下方“构建失败的判定”）。

## Answer

**2026-11-10 定稿。**

### 1. 评审要点单（改为现有“用 Qoder 审查此 MR”复制内容的正文）

成本为零：`startReview` 已经拉了 diff（`getMrDiffs`，≤ 3 页 × 100 文件），只是把事实写进文案。模板：

```
/code-review 审查 GitLab MR !{iid}（{title}），链接 {url}，diff 已保存到 {diffPath}

事实：
- 改动 {n} 个文件（+{add} / −{del}）
- 目录：{dir ×count}、…（按路径前两段聚合）
- 敏感变更：{命中的规则}（无命中则不写这行）
- 关联 Jira：{key}（{summary}）
- 已批准：{names}；{还差 N 个 或 已齐}

只审这个 MR 的改动，不要审当前工作区。
```

敏感变更规则（固定集合，不做模型判断）：`*.vcxproj / *.props / *.sln`、`package.json`、`scripts/**`、`src/models/**`（扩展与 WebView 共享）、`*.sql`、含 `migration` 的路径。

### 2. 卡面信号

| 信号 | 位置 | 形态 |
|---|---|---|
| MR 有冲突（`has_conflicts`） | MR 卡面 | 红字标签“有冲突” |
| MR 有未解决讨论（`blocking_discussions_resolved=false`） | 仅详情 | 一行“N 条未解决讨论” |
| Jira 卡合入后未推进（`mrs[].mergedAt`） | 仅详情 | “合入后 3 天未推进”（阈值 3 天写死） |
| 构建失败 | Jira 卡面 | 红字“构建失败 #F”（可点直达 Jenkins） |

### 3. 构建失败的判定（能判“在不在”，不能判“是不是它引起”）

能确定的：失败构建里**包不包含**这次合入（`merge_base` 前先祖先判定，同 06）。
不能确定的：失败是否由它**引起**（一天两次构建，一次含多个合入，且只读不到失败阶段与日志）。

所以分两种情形，只在高嫌疑时上卡面：

- **曾成功过**：存在一个**更早的成功构建**也包含该合入 ⇒ 本次失败与新引入无关，**不上卡面**（否则分支一红，所有卡都红，信号立刻失效）
- **从未成功过**（且最新已完成构建为 FAILURE）⇒ 高嫌疑：卡面标红“构建失败 #F”；详情补一句“本次构建新引入的合入共 N 个”（同批次靠 `compare` 得出），并明写“不断定是它引起的”

实现上配合 06：`buildFailed` 从“时间窗内有失败”改为上述祖先判定 + “从未成功过”两个条件。

### 4. 提醒与降级

- **无 toast、无状态栏闪烁**；只在板内与卡面表现
- 取数失败：从未成功过 → 按钮/标签置为“数据未知、不可用”；`stale` → 照常可用，文案末尾加“（取自 {时间} 的数据，可能已过期）”
- diff 拉取失败：沿用现有降级（复制只带链接的审查指令 + 一条 warning）

### 5. 明确不做

- 催审文案
- 构建失败的一键复制（链接直达比一段话更短；复制出来的文本也没有去处）
- 本地待办清单 / toast / 状态栏入口

### 落地影响

- `GitLabMrRow` / `MrCard`：增 `hasConflicts`、`blockingDiscussionsResolved`（列表接口默认返回，无额外请求）
- `GitLabService.getMrDiffs`：需同时返回文件列表与增删行数（现在是拼成一个字符串，要拆成结构体）
- `MrReviewHandoff.buildReviewRequest`：改为结构化事实拼文案（保持纯函数，可单测）
- `DeliveryStageResolver`：`buildFailed` 口径按第 3 节改写（与 06 一起改）
- `MrCard.tsx` / `Card.tsx` / `DetailPanel.tsx`：新增标签与详情行
